# Network Test Requirements

This document defines the common correctness rules for KPro network transports.
New message-based transports should follow these rules before they are treated
as production-ready in this repository.

The current reference implementation is the TCP test set in:

- `test/tcp_wire_crc_test.go`
- `test/tcp_file_compare_test.go`

## Scope

These rules apply to message-based transports:

- TCP
- UDP
- WebSocket
- Any future transport that carries `core.Message` through `protocol.KProV1`

HTTP and SSE are path or stream oriented transports. They should still test
ordering and error behavior, but they do not have to use the KProV1 frame CRC
rules unless they are explicitly adapted to `core.Message`.

## Trace Points

Every message-based transport test should be able to record four logical trace
streams:

| Trace | Meaning |
| --- | --- |
| `client_sent` | Encoded application frame sent by the client |
| `server_received` | Encoded application frame decoded by the server transport |
| `server_sent` | Encoded application frame sent by the server |
| `client_received` | Encoded application frame decoded by the client |

For TCP, the application frame is the KProV1 frame on the byte stream.

For UDP, the application frame is the KProV1 frame inside one datagram.

For WebSocket, the application frame is the binary message payload after
WebSocket frame reassembly. Raw WebSocket bytes are not stable for equality
because client frames are masked and messages may be fragmented.

Each trace record should include at least:

| Field | Requirement |
| --- | --- |
| `index` | Monotonic trace index within the trace stream |
| `seq` | `core.Message.Seq` |
| `msg_id` | `core.Message.ID` |
| `flags` | `core.Message.Flags` |
| `payload_len` | Payload byte length |
| `frame_len` | Encoded application frame byte length |
| `crc32` | CRC32 of the encoded application frame |
| `frame_hex` | Hex string of the encoded application frame |

`crc32` is for readable diagnostics. The authoritative equality check should
still compare `frame_hex`, because CRC alone can collide.

## Core Correctness Rules

### R1: Client To Server Frame Integrity

For every accepted request:

```text
client_sent == server_received
```

The comparison must check count, frame length, CRC32 and full frame bytes.

For single-connection ordered cases, compare by exact trace order.

For cases where global order is intentionally not guaranteed, compare as a
multiset of full frame bytes.

### R2: Server To Client Frame Integrity

For every response generated by the server:

```text
server_sent == client_received
```

The comparison must check count, frame length, CRC32 and full frame bytes.

For single-connection ordered cases, compare by exact trace order.

For async or multi-connection cases where completion order is intentionally not
guaranteed, compare as a multiset unless the scenario explicitly defines an
expected completion order.

### R3: Sync Handler Ordering

For a single connection and `HandleSync` route:

```text
client_sent order
  == server_received order
  == handler execution order
  == server_sent order
  == client_received order
```

This is the strictest ordering rule and should be tested with multiple messages,
not only one request.

### R4: Async Handler Ordering

For a single connection and `HandleAsync` route:

```text
client_sent order == server_received order
```

Response completion order is not guaranteed when more than one async worker can
run. Tests must verify content integrity for all responses, but they must not
require request order unless the route or configuration explicitly serializes
async work.

If a test intentionally blocks one async handler and lets another finish first,
the expected result should prove that out-of-order responses are allowed.

### R5: Mixed Sync And Async Ordering

For one connection with mixed sync and async routes:

```text
client_sent order == server_received order
```

Sync routes keep their own serialized processing path. Async routes may complete
before earlier sync requests if they are dispatched to async workers and the sync
path is blocked.

Tests should explicitly document the expected response order for mixed cases.

### R6: Multi-Connection Ordering

Different connections are concurrent by default.

The framework must preserve frame integrity per connection, but it must not
promise global ordering across different connections unless a future feature
adds explicit global serialization.

Required behavior:

- A blocked handler on connection A must not block connection B.
- Each connection must receive only its own responses.
- Global trace comparison across all connections should use set equality unless
  the test adds a deterministic scheduler.

### R7: Response Correlation

Every response must preserve the request correlation fields unless the scenario
defines a different response:

```text
response.Seq == request.Seq
response.ID  == request.ID
```

For framework-generated errors:

```text
response.Seq == request.Seq
response.ID  == core.MsgError
response.Data contains the expected error text
```

For heartbeat:

```text
request.ID   == core.MsgHeartbeat
response.ID  == core.MsgPong
response.Seq == request.Seq
```

Heartbeat should bypass the business router.

### R8: Payload And Flags Preservation

Echo-style tests must verify:

- Payload bytes are unchanged.
- Empty payloads work.
- Boundary payload sizes work.
- `core.Message.Flags` is preserved when the handler echoes it.
- Binary data is tested, not only printable text.

### R9: Backpressure And Limit Errors

Transport tests must cover configured limits:

- Sync queue full.
- Async queue full.
- Max in-flight requests per session.
- Router closed while requests are being dispatched.
- Small send queue with paced read/write.

Expected behavior:

- Accepted requests are either handled correctly or receive the correct
  framework error.
- Error responses keep the original request `Seq`.
- The connection does not silently drop accepted requests without a traceable
  response unless the protocol fault requires connection close.

### R10: Transport Fragmentation And Batching

Stream and frame transports must prove that application messages survive
transport-level segmentation:

- TCP coalesced writes: multiple KProV1 frames in one network write.
- TCP fragmented writes: one KProV1 frame split across multiple network writes.
- WebSocket fragmented message: one KProV1 frame split across continuation
  frames and reassembled before protocol decode.
- UDP does not provide stream fragmentation at this layer; each datagram should
  contain exactly one complete KProV1 frame unless a future UDP fragmentation
  layer is added.

The integrity comparison must still pass after reassembly.

### R11: Protocol Fault Handling

Protocol fault tests should include:

- Bad magic.
- Bad version.
- Declared length too large.
- Short header.
- Partial body.
- Abrupt close with partial frame.

Expected behavior:

- Invalid input is rejected.
- The server does not decode a corrupt frame as a valid `core.Message`.
- The server does not panic.
- The connection may close when the transport cannot recover frame boundaries.

### R12: Shutdown And Half-Close

Tests should include graceful and partial close behavior:

- Client half-closes after completed round trips.
- Server shutdown closes listener and active sessions.
- Already-sent responses are flushed when the transport design promises it.
- Blocked queues unblock on session close or router shutdown.

## Minimum Scenario Matrix

Every message-based transport should eventually cover this matrix:

| Scenario | Required |
| --- | --- |
| Single request echo | Yes |
| 1000-message sync echo | Yes |
| 1000-message async echo | Yes |
| Mixed sync and async routes | Yes |
| Unknown handler error | Yes |
| Heartbeat to pong | Yes |
| Queue full errors | Yes |
| Max in-flight errors | Yes |
| Router closed errors | Yes |
| Multi-connection isolation | Yes, when the transport supports connections |
| Payload boundaries | Yes |
| Flags preservation | Yes |
| Transport batching or fragmentation | Yes, when applicable |
| Protocol fault input | Yes |
| Close and shutdown behavior | Yes |

Connectionless transports such as UDP should replace multi-connection isolation
with peer/session isolation if the transport maps remote addresses to sessions.

## Acceptance Bar

A transport passes the network correctness bar when:

1. All required scenarios pass consistently.
2. Frame integrity is verified by full encoded frame equality, not only by
   decoded `core.Message`.
3. Ordering assertions match the documented semantics of sync, async and
   multi-connection execution.
4. Error paths are checked with concrete `Seq`, `MsgID` and payload assertions.
5. The tests include both normal traffic and malformed input.

Performance benchmarks are useful, but they do not replace these correctness
requirements.
