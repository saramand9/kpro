## 目标与边界

近期目标是交付一个**在明确业务负载和部署规格下经过验证的生产级 v1**。
长期争取成为 Go 多协议业务服务这一细分方向的技术标杆，重点是资源可控、
停机可靠、业务接入简单，以及可持续维护。

评价分成三个层次：

1. 工程基础：机制、契约和仓库测试存在，能够用于业务开发与试点。
2. 生产级 v1：选定场景的正确性、容量、运维和升级门槛均有可复核证据。
3. 细分场景标杆：在上述基础上，多个独立业务持续采用，经历多个版本及故障
   恢复，并形成可复现的技术优势与持续维护能力。

行业认可无法由功能数量、一次跑分或一个主观分数保证。当前仍遵守
[API Stability](api-stability.md) 的 pre-1.0 政策；本文不改变发布状态，
也不提前承诺容量、可用性或兼容性。

继续保持以下边界：

- 认证、授权和身份策略由应用或网关负责。
- `server` 保持依赖中立，遵守 [Dependency Boundaries](dependency-boundaries.md)。
- 保留 HTTP、SSE、gRPC 等协议原生处理方式，不为形式统一增加业务接入负担。
- 新增协议、适配器或调度模式，应说明具体业务需求、维护成本及验收方式。
- 写入回执和出站 drain 表示传输写入结果；业务确认、持久化交付、重试与幂等
  仍须按 [Production Readiness](production-readiness.md) 设计。

## M0：先完成契约和基线收敛

状态：进行中。以下任务均待实施。

### P0-1：统一 TCP 写批处理契约

已知观察：

- [TCP Config](../transport/tcp/server.go) 将 `MaxWriteBatchFrames` 描述为
  单次队列拉取的帧数上限，当前默认值是 32。
- [批写实现](../transport/tcp/batch_writer.go) 在积压达到该值且队列允许时，
  会把拉取额度翻倍，最多到 `SendQueueSize`；默认配置下可取到 64 帧。
- [Performance Fast Paths](performance-fast-path.md) 的 TCP 段仍写默认 16 帧，
  且逐次提交的写超时描述与实现中的期限刷新窗口需要重新核对。

实施顺序：先为超过显式配置上限的行为建立回归用例，再确定最小修正。
优先保留 `Max` 参数的硬上限含义；如需自适应批量，清楚区分基准量与硬上限，
说明行为兼容性和性能影响。分别核对 TCP 与 WebSocket，不做跨协议的数值替换。

验收条件：

- [ ] 显式小批量、默认批量、队列积压和字节切分的行为符合选定契约。
- [ ] 配置注释、默认值、实现、测试和性能文档一致，包含合并等待与超时语义。
- [ ] 保留 FIFO、负载所有权、短写报错、回执完成和错误路径资源释放行为。
- [ ] TCP 相关测试、确定性故障注入、race 和受影响的性能预算通过；比较保留的
  代表性工作负载，记录吞吐、CPU 和尾延迟变化，不能只凭微基准接受优化。

### P0-2：形成可部署的资源预算

当前 TCP 默认出站记账额度为：

```text
每会话：64 × (65,536 + 20) = 4,195,584 字节，约 4 MiB
10,000 个会话：41,955,840,000 字节，约 39.07 GiB
```

这是配置额度的组合计算，并非预分配内存或实测 RSS。它表明单会话有界仍需
结合实例容量做配置。实际预算还要计入负载池容量取整、读缓冲、Router 工作、
连接状态、协议栈和其他组件。详见 [Operations](operations.md)。

验收条件：

- [ ] 为代表性部署规格记录连接数、报文大小、队列与字节额度、超时及总内存预算。
- [ ] 说明预算由哪些现有配置保证，并通过测量判断是否需要共享的出站总预算。
- [ ] 慢消费者与过载测试中，内存、排队和等待者数量保持在声明范围内；健康
  客户端的表现、拒绝或断开策略及压力解除后的恢复均有记录。
- [ ] 告警和运维说明能对应实际计数器，应用能够理解和处理拒绝、超时及关闭。

### P0-3：建立可复核的干净基线

- [ ] 在干净检出记录提交、工具链、平台、依赖状态和完整命令。
- [ ] 按 [Analysis Index](analysis-index.md)、[CI](../.github/workflows/ci.yml)
  和 [API Stability](api-stability.md) 完成适用的测试、race、vet、依赖校验、
  漏洞扫描、生成检查、性能预算及发布门槛。
- [ ] 对所支持的数据库运行真实引擎集成测试，并记录引擎版本和拓扑。
- [ ] 保留失败样本及处理记录；对再次出现的端口错误或超时定位原因。
- [ ] 归档可追溯的日志或 CI 运行链接，明确跳过项；缺失必需证据时不标记通过。

M0 退出条件：P0-1、P0-2、P0-3 完成，并有证据支持进入容量验证。

## M1：验证明确负载下的容量与故障行为

状态：未开始。首先选定一个代表性业务，记录协议组合、连接数、请求速率、
报文分布、TLS、下游延迟和部署规格，并在运行前定义通过阈值。

- [ ] 使用目标 Linux 环境和独立压测机，记录 CPU、内核、网络、工具链、配置、
  服务端及客户端源版本；先确认负载发生器没有成为瓶颈。
- [ ] 覆盖小消息、大消息、突发流量、慢消费者、连接重建和下游变慢；遵守
  [现有性能测量约定](performance-fast-path.md) 中适用的公平性与正确性要求。
- [ ] 保留成功吞吐、错误分类、p50/p95/p99/p99.9、CPU/消息、RSS/堆、goroutine、
  排队和 drain 时间；逐场景判定，平均值不能掩盖失败场景。
- [ ] 进行跨峰谷的持续运行。建议初始项目门槛为至少 24 小时，再按业务周期
  扩展；时长和阈值须预先记录。这是项目建议，不是行业统一认证标准。
- [ ] 注入断连、短写、超时、依赖不可用、停机和重启，验证故障后的资源回收与
  恢复；在正常与过载条件下均检查健康客户端和数据正确性。
- [ ] 归档原始样本、复现步骤、样本波动及限制，按
  [Benchmark Results](../benchmark/RESULTS.md) 的证据要求维护结果。

M1 退出条件：每个承诺支持的场景均满足预先声明的正确性、容量和恢复门槛。
未测或失败场景保持明确限制，不由其他场景的结果替代。
